# Вкладка «UI-окна»: план и фундамент

> **Статус:** подготовка (Core-фундамент готов, вкладки в оболочке ещё нет).
> **Дата:** 18.11.2026.
> **Код:** `dotnet/src/XRayForge.Core/GameUi/`, тесты — `dotnet/tests/XRayForge.Tests/GameUiTests.cs`.

## 1. Задача

Дать модмейкеру редактировать интерфейс игры без внешних инструментов: открыть файл
`gamedata/config/ui/*.xml` (SoC/CS) или `gamedata/configs/ui/*.xml` (CoP), увидеть окно целиком,
выделить элемент, поправить координаты, размеры, текстуры, тексты и подсказки, добавить или
удалить элемент — и сохранить файл так, чтобы игра его приняла.

Прежний клиент (React, удалён 18.11.2026) такой вкладки не имел: там был только дескриптор
текстур `ui_*.xml` (`textures_descr`). Поэтому паритет-порт не нужен — это новая фича, и её
нужно проектировать по реальным файлам игр.

## 2. Что такое UI-файл X-Ray

Проверено на 294 файлах из `stalk-src/SoC` и `stalk-src/CoP` (154 + 140):

- Корень — `<window>` (SoC) или `<w>` (CoP); декларация XML бывает, но часто отсутствует.
- Имя тега — это класс элемента движка (`static`, `button`, `text`, `list`, `edit`,
  `progress_bar`, `frame`, `scroll_view`), но моды добавляют произвольные
  (`indicator_booster_psy`, `shniaga_wnd`, `back_movie`). Набор тегов открытый.
- Координаты `x`/`y` — смещение относительно родителя, `width`/`height` — размер.
- Значение может быть атрибутом (`caption="ui_mm_newgame"`) или прямым текстом
  (`<texture>ui_menu_backgraund</texture>`).
- Встречаются комментарии с двойным дефисом (`<!--- … --->`), строки `#include` вне тегов,
  атрибуты без значения, незакрытые элементы — строгий `XDocument` на них падает.
- Кодировка — Windows-1251 или UTF-8 (декларация может врать), плюс CRLF/LF и табы.

## 3. Что уже сделано (Core, без WPF)

| Класс | Назначение |
|---|---|
| `GameUiParser` | Толерантный разбор текста в дерево с диапазонами (`Start`/`OpenTagEnd`/`ContentStart`/`CloseTagStart`/`End`) и диагностикой (`uiUnclosedTag`, `uiUnexpectedClose`, `uiUnclosedComment`, `uiUnclosedQuote`, `uiEmptyTag`). |
| `GameUiDocument` | Файл: корни, текст, диагностика, `Canvas`, адресация `0.2.1` (`Find`, `PathOfElement`), поиск `FindAll`/`FindTag`. |
| `GameUiElement` | Тег, атрибуты в порядке файла, дети, прямой текст, `Rect`, `Number`/`Flag`, `Kind`, `Descendants`/`Ancestors`. |
| `GameUiElementCatalog` | Классификация тегов (`Window`/`Static`/`Button`/`Text`/`List`/…), типы атрибутов (`Number`/`Flag`/`Alignment`/`Font`/`Texture`), `align`-алиасы, подсказки для новых элементов, глифы и ключи локализации. |
| `GameUiLayout` | Абсолютная геометрия через вложенность (`GameUiPlacement`), хит-тест верхнего элемента, дети размещения, `Clamp` в холст 1024×768. |
| `GameUiEditor` | Точечные правки: `SetAttribute`/`RemoveAttribute`/`RenameTag`/`SetInnerText`, `AddChild`/`RemoveElement`/`MoveElement`, `MoveBy`/`ResizeBy`, `Serialize` (полная пересборка — только для новых файлов). |
| `GameUiTemplates` | Новое окно, элементы палитры (static/button/text/list/edit/progress/frame), свободное имя `new_static_2`. |

Ключевое решение: правки идут по смещениям в исходном тексте, а не пересборкой файла. Комментарии,
`#include`, порядок атрибутов и форматирование остальных элементов сохраняются — модмейкер не
получает «диф на весь файл». После каждой правки модель пересобирается, а элементы адресуются
строкой `0.2.1`, поэтому ViewModel хранит адрес, а не ссылку на объект.

Проверка: 24 теста (`GameUiTests`), зонд на 294 реальных файлах — 0 ошибок разбора
(6 файлов содержат только комментарии/пустые).

## 4. Этапы реализации вкладки

1. **Core-фундамент — сделано.** Парсер, модель, каталог, геометрия, редактор, шаблоны.
2. **Данные проекта.** `Project.UiFiles` (`Dictionary<string,string>` путь → текст, как
   `LtxFiles`/`ItemFiles`), поле в `ProjectMigration.Empty`, чтение в `GamedataScanner`
   (ветка для путей с `/ui/`, кодировка через `GameEncoding`), снапшот `AppDataService`,
   round-trip `saves/*.project.json`.
3. **ViewModel.** `UiWindowsViewModel`: список файлов + фильтр, `Attach(project)`,
   `RefreshLocalization`; `UiElementViewModel` (дерево по адресам), `UiPropertyViewModel`
   (тип значения из каталога), `UiPreviewViewModel` (размещения из `GameUiLayout`),
   команды добавления/удаления/перемещения/дублирования, откат через `History`.
4. **View.** Три панели: файлы | холст 1024×768 с сеткой и выделением | дерево + свойства.
   Ширины — `GridSplitter` + `ProgramSettings`, стили — `SideCard`/`FieldLabel`/`CompactInput`,
   строки — только ключи локализации (RU/EN).
5. **Экспорт.** Сохранение в `gamedata` по исходному пути и включение ui-файлов в `GamePackage`
   (отдельная категория манифеста).
6. **Проверка и документация.** Debug/Release build и test, UI-зонд на временном профиле,
   `MIGRATION.md`, матрица в `FEATURE_GAP_AMK.md`.

## 5. Ограничения первой версии

- Предпросмотр — геометрический: рамки, заливка класса, имя элемента, текстура подписью.
  Полный рендер DDS/шрифтов движка не планируется (это отдельный пласт, как Level Editor).
- `stretch`, `alignment`, `complex_mode` сохраняются и редактируются, но не влияют на
  предпросмотр так, как в движке: точное поведение X-Ray UI без запуска игры не воспроизвести.
- Виртуальные списки (`list` с динамическими строками), скроллы и анимации показываются
  как рамки — их содержимое задаётся скриптами, а не XML.
- Перетаскивание — по сетке 1 px с привязкой к 8 px (Shift — без привязки); групповое
  выделение и выравнивание — после базовой вкладки.

## 6. Риски и как их снимаем

| Риск | Решение |
|---|---|
| Файл не разбирается строгим XML | свой толерантный парсер + диагностика по кодам (уже есть) |
| Правка портит форматирование и комментарии | точечные замены диапазонов, полная пересборка — только для новых файлов |
| Кодировка при сохранении | `GameEncoding.Decode` при импорте, `Encode` с исходной декларацией при экспорте |
| Моды с собственными тегами | открытый каталог: неизвестный тег редактируется как обычный, геометрия берётся из атрибутов |
| Потеря координат при вложенности | `GameUiLayout` считает абсолютные прямоугольники, правки пишут локальные значения |
| Ссылки на элементы после правки | адресация `0.2.1`, после каждой правки ViewModel берёт свежий элемент |
