# Обзор кода X-Ray Forge (WPF)

> **Дата ревизии:** 18.11.2026
> **Область:** `dotnet/src/XRayForge.Core`, `dotnet/src/XRayForge`, `dotnet/tests/XRayForge.Tests`,
> `dotnet/docs`, `MIGRATION.md`.
> **Характер работы:** правки в код не вносились — только этот документ и запись в `MIGRATION.md`.
> **Проверка:** `dotnet build dotnet/XRayForge.sln -c Debug` — 0 предупреждений / 0 ошибок;
> `dotnet test dotnet/XRayForge.sln -c Debug --no-build` — **424/424** (386 атрибутов
> `[Fact]`/`[Theory]`, из них 10 теорий с 48 `[InlineData]`).

Документ фиксирует три категории находок по каждому модулю:

| Категория | Что означает |
|---|---|
| **Недоработки** | функциональность заявлена, но не доделана либо работает неверно (дефект, риск) |
| **Улучшения** | работает, но хрупко, медленно или расходится с правилами проекта |
| **Добавить** | возможности нет, но она нужна по `FEATURE_GAP_AMK.md` или сценариям модов |

Приоритеты: **P1** — потеря данных, падение, неверный игровой экспорт; **P2** — техдолг,
ломающий сценарии на реальных проектах; **P3** — удобство, косметика, страховка на будущее.

Ссылки — от корня репозитория в виде `путь:строка`. Пункты, которые нужно подтвердить на живых
данных, помечены «(проверить)».

Известные функциональные пробелы (спавн, торговля, ассеты, уровни) здесь **не дублируются** —
они ведутся в `dotnet/docs/FEATURE_GAP_AMK.md`; в §2.3 и §5 отмечено только то, что расходится
с текущим кодом.

## 2. Core

### 2.1. Projects — модель, миграции, сериализация

Файлы: `Project.cs`, `ProjectReader.cs`, `ProjectMigration.cs`, `ProjectSerializer.cs`,
`ProjectIntegrity.cs`, `InternalXml.cs`, `EquipSlotCatalog.cs`.

**Недоработки**

- **P2 · Версия схемы при чтении принудительно ставится текущей.** `ProjectMigration.cs:28`
  (`p.Version = ProjectSchema.Version`), тогда как `MigrateLegacy` ставит `4`
  (`ProjectMigration.cs:140`, `Project.cs:12-15`).
  Файл, сохранённый более новой версией редактора, читается эвристикой «как есть», а при следующем
  сохранении версия перезаписывается на 3 — откатить это без бэкапа нельзя.
  **Сделать:** брать `version` из файла; если он больше `ProjectSchema.Version` — предупреждать
  и работать в режиме «только чтение» либо сохранять рядом копию.
- **P3 · Внутренний XML диалога доступен только в Debug.** `ShellViewModel.cs:1130-1133`
  (`if (!IsDebugBuild) return;`). В Release нет ни предпросмотра, ни копирования в буфер —
  диагностировать нечего. **Сделать:** оставить файловый экспорт Debug-овским, но добавить
  просмотр/копирование в окне (или явно описать ограничение в справке).

**Улучшения**

- **P2 · `ToPersistable` дважды сериализует проект.** `ProjectSerializer.cs:44-54`:
  `SerializeToElement` → `Deserialize<Project>` ради снятия тяжёлых полей (`ltxFiles`,
  `textures`, `scripts`, `itemFiles`, `itemOrigins`). На проекте с тысячами квестов/диалогов
  это выполняется при **каждом** автосохранении (раз в 60 с по умолчанию,
  `ProgramSettings.cs:23`).
  **Сделать:** клонировать явным copy-конструктором либо вынести тяжёлые поля в отдельный
  DTO-слой, который не участвует в записи профиля.
- **P2 · Перезапись неизменённого файла.** `ProjectSerializer.Serialize` пишет с отступами
  (`WriteIndented = true`, `ProjectSerializer.cs:19`), а `AppDataService.SaveCurrentProject`
  (`AppDataService.cs:60`) вызывает запись без сравнения с предыдущим содержимым.
  **Сделать:** хранить хэш последней записи и пропускать запись, если проект не менялся —
  это заодно снимет часть риска из §2.2.
- **P3 · Нет структурной валидации после миграции.** `ProjectMigration.Migrate`
  (`ProjectMigration.cs:23-76`) нормализует типы, но не проверяет согласованность (серия vs
  `gamedataPath`, дубликаты `dialogueId`, неизвестные `series`). Ошибки всплывают позже —
  в `ProjectIntegrity` (`ProjectIntegrity.cs`) или в экспорте.
  **Сделать:** отдельный шаг «нормализация + отчёт» с теми же кодами проблем, что у
  `ProjectIntegrityIssue`.

**Добавить**

- Ротация копий `.project.json` перед перезаписью (`.bak` + N версий). Сейчас история копий
  только ручная (`ShellViewModel.AddBackup`, `AppDataService.AddBackup`).
- Переносимый пакет проекта («проект + ресурсы») — ZIP умеет только игровые текстовые файлы
  (§2.3), сам `.project.json` в пакет не попадает.

### 2.2. Storage — профиль, автосохранение, файловые операции

Файлы: `AppDataService.cs`, `AutosaveService.cs`, `FileSystemService.cs`, `ProgramSettings.cs`,
`ProjectFileService.cs`, `AppDataModels.cs`.

**Недоработки**

- **P1 · «Сохранить» не перехватывает ошибки ввода-вывода.**
  `ShellViewModel.cs:449-464` последовательно вызывает `SaveCurrentProject`, `SaveProject`,
  `SaveGamedataSnapshot`; `AppDataService.WriteFile` (`AppDataService.cs:314-318`) — это
  `File.WriteAllText` без `try/catch`, а `ProjectFileService.SaveProjectFile`
  (`ProjectFileService.cs:27`) — тоже. Любая ошибка (нет прав, диск занят, файл открыт другой
  программой) уходит из `RelayCommand` в необработанный обработчик WPF — приложение падает
  ровно на кнопке «Сохранить». В `ScanGamedataAsync` тот же `Save()` прикрыт общим `catch`
  (`ShellViewModel.cs:988`), а в команде — нет.
  **Сделать:** `try/catch` вокруг каждой записи, локализованный ключ ошибки (`saveFailed`),
  отдельная обработка ошибки снапшота, чтобы проект сохранялся даже без снапшота.
- **P1 · Запись профиля не атомарна.** `AppDataService.WriteFile` (`AppDataService.cs:314-318`).
  `File.WriteAllText` поверх существующего файла: прерывание (закрытие процесса, BSOD, антивирус)
  оставляет обрезанный JSON, а `LoadCurrentProject` через `TryDeserialize`
  (`AppDataService.cs:296-301`) вернёт `null` — проект «исчезает» без сообщения.
  **Сделать:** писать в `<file>.tmp`, затем `File.Replace`/`File.Move(overwrite: true)`,
  при старте подхватывать `.tmp`/`.bak`, если основной файл битый.
- **P1 · Автосохранение игнорирует флаг `Dirty`.** `AutosaveService.Tick`
  (`AutosaveService.cs:80-92`) всегда пишет проект и снапшот; `Dirty` объявлен
  (`AutosaveService.cs:34`) и выставляется оболочкой (`ShellViewModel.cs:1362-1366`), но
  в `Tick` не читается. Итог: запись десятков мегабайт каждую минуту даже без правок.
  **Сделать:** `if (!Dirty) return false;` перед записью.
- **P1 · Автосейв идёт с пула потоков параллельно UI-сохранению.**
  `AutosaveService.Start` использует `System.Threading.Timer` (`AutosaveService.cs:63-68`),
  то есть `Tick` выполняется не в потоке диспетчера, а `_store` — общий с `Save()`.
  Два одновременных `File.WriteAllText` одного файла (см. выше) + отсутствие атомарности дают
  реальную вероятность битого `current.project.json`.
  **Сделать:** `SemaphoreSlim` вокруг записи либо маршалить автосейв в UI-диспетчер.
- **P3 · Таймер глотает только I/O-исключения.** `AutosaveService.cs:65-67` ловит
  `IOException`/`UnauthorizedAccessException`; `JsonException`/`NotSupportedException` пойдут
  наружу из потока таймера — необработанное исключение в ThreadPool-потоке убивает процесс.
  **Сделать:** ловить `Exception`, публиковать событие ошибки и показывать статус.

- **P1 · Закрытие окна не проверяет несохранённые правки.** `MainWindow.xaml.cs:27` —
  `Closed += (_, _) => _shell.Dispose();`, а `ShellViewModel.Dispose` (`ShellViewModel.cs:1446-1453`)
  только снимает обработчик и останавливает таймер. Нет обработки `Closing`, нет проверки `Dirty`
  и нет финального сохранения: пользователь теряет правки, нажав крестик.
  **Сделать:** `Closing` → если `Dirty`, диалог «Сохранить / Не сохранять / Отмена»;
  перед выходом вызвать `_autosave.Tick()` (или `Save()`), затем `Dispose`.
- **P2 · `"hotkeys": null` в `settings.json` роняет загрузку настроек.**
  `ProgramSettingsCatalog.Normalize` (`ProgramSettings.cs:99-124`) на строке 103 делает
  `foreach (var pair in source.Hotkeys)` без проверки на `null`; `System.Text.Json` штатно
  присваивает `null` ссылочному свойству при явном `null` в файле, а `FromJson` ловит только
  `JsonException` (`ProgramSettings.cs:131-140`). Вызов идёт из
  `AppDataService.LoadProgramSettings` при каждом запуске.
  **Сделать:** `source.Hotkeys ?? new()` и `catch (Exception)` с фолбэком; тест на
  `{"hotkeys":null}`.
- **P2 · Импорт битых настроек затирает профиль дефолтами.** `ShellViewModel.ImportSettings`
  (`ShellViewModel.cs:1185-1209`): `ProgramSettingsCatalog.FromJson` при невалидном JSON
  возвращает `Fallback()` (`ProgramSettings.cs:139`), после чего строка 1207 вызывает
  `SaveProgramSettings()` → в `settings.json` записываются значения по умолчанию без
  предупреждения. **Сделать:** отличать «пустой файл» от «битый», при ошибке — вопрос
  «заменить настройки?», бэкап прежнего файла.
- **P3 · `ReadFile` не отличает «нет файла» от «нет доступа».** `AppDataService.cs:303-312`:
  оба случая → `null`, и вызывающий код молча работает с дефолтами. Не хватает диагностики
  (правило 00-project: без «магических» строк статуса, но с сообщением пользователю).

**Улучшения**

- **P2 · Снапшот gamedata и `saves/<имя>.project.json` рассинхронизируются.**
  `ProjectSerializer.ToPersistable` (`ProjectSerializer.cs:44-54`) намеренно выкидывает
  `ltxFiles`, `textures`, `scripts`, `itemFiles`, `itemOrigins` из файла проекта — они живут
  только в снапшоте (`ShellViewModel.cs:457`, `AppDataService.ToSnapshot`). Если снапшот
  потерян/устарел (например, сохранение снапшота упало, а проект записался), открытие проекта
  даёт «пустые» скрипты и LTX без единого предупреждения.
  **Сделать:** версию/хэш снапшота в `Project` и проверку согласованности при загрузке.
- **P3 · `AutosaveService.ApplySettings` не сбрасывает `LastAutosave` и обнуляет интервал.**
  `AutosaveService.cs:43-54` + `Stop()` (72-77): после остановки `IntervalSeconds == 0`,
  а статус продолжает показывать «автосейв включён». **Сделать:** отдельное поле
  «настроенный интервал» и явный статус «выключено».
- **P3 · Обход каталога: массивы и рекурсия.** `FileSystemService.Walk`
  (`FileSystemService.cs:37-82`) сразу материализует `Directory.GetFiles/GetDirectories`
  (на gamedata это десятки тысяч путей), рекурсия без ограничения глубины и без отмены.
  **Сделать:** `EnumerateFiles`/`EnumerateDirectories` с `EnumerationOptions.IgnoreInaccessible`,
  явный стек, `CancellationToken`.
- **P3 · `ReadGameText` читает файл целиком без ограничения размера.**
  `FileSystemService.cs:103-104`. Для больших `.ltx`/`.xml` — риск OOM на слабых машинах.
  **Сделать:** порог размера + потоковое чтение для крупных файлов.

**Добавить**

- Восстановление профиля после сбоя: при старте, если `current.project.json` битый, предложить
  `.tmp`, последний бэкап или снапшот.
- Автоматическая ротация автосейвов (`saves/<имя>.autosave.N.json`) с ограничением из
  `ProjectSchema.BackupsLimit`.
- Экспорт/импорт всего профиля (настройки + проекты + бэкапы) одним архивом — сейчас
  экспортируются только настройки (`ShellViewModel.cs:1159-1183`).

### 2.3. Dialogs и Export — сборка игровых файлов

Файлы: `Dialogs/DialogueGameExport.cs`, `Dialogs/DialogueFiles.cs`, `Dialogs/TextIdTools.cs`,
`Export/GamePackage.cs`, `Quests/QuestExport.cs`, `Projects/InternalXml.cs`.

**Недоработки**

- **P1 · Игровой пакет неполный.** `GamePackage.TextFiles` (`GamePackage.cs:18-58`) собирает
  только диалоги, квесты, `system.ltx` и скрипты. Нет `character_desc_*.xml` (персонажи),
  `items.ltx`, `textures_descr`, торговли, спавна и инклюдов из `project.LtxFiles`.
  Это совпадает с долгом P0 в `FEATURE_GAP_AMK.md:212-214`, поэтому здесь фиксируется как
  «экспорт персонажей и предметов» для планирования, а не как новая идея.
  **Сделать:** добавить экспорт персонажей (`character_desc_<id>.xml`) и `items.ltx`
  (`ItemsViewModel` уже умеет отдавать текст, `ItemsViewModel.cs:930-940`).
- **P3 · Смешанный формат квестов теряется.** `GamePackage.cs:29-43`: если в проекте есть
  **хотя бы один** `task_manager`, генерируются `task_manager.ltx/xml`, иначе — `game_tasks.xml`.
  Проект с квестами обоих форматов экспортируется частично.
  **Сделать:** группировать по `Format` и собирать оба набора файлов.
- **P3 · Скрипты с пустым текстом пропадают молча.** `GamePackage.cs:50`:
  `if (string.IsNullOrWhiteSpace(script.Name) || string.IsNullOrEmpty(script.Text)) continue;`
  — ни статуса, ни отчёта. **Сделать:** возвращать `Skipped` рядом с `Files` и показывать
  в результате экспорта.

**Улучшения**

- **P2 · Ключи карты не проверяются на выход из каталога.** `GamePackage.NormalizePath`
  (`GamePackage.cs:91-92`) сохраняет `..`, а `DialogueGameExport.TargetPath`
  (`DialogueGameExport.cs:115-138`) делает `Path.GetFullPath(Path.Combine(root, relative))`
  без проверки, что результат остался внутри `root`. Путь вида `gamedata/../../x` (может прийти
  из `ScriptFile.Path`, `GamePackage.cs:51-54`) запишет файл вне выбранной папки.
  **Сделать:** после нормализации сравнивать префикс с `root + Path.DirectorySeparatorChar`
  и отклонять выход (или `Path.GetRelativePath` + проверка на `..`).
- **P2 · `WriteZip` дублирует расчёт.** `GamePackage.cs:86-88`: `TextFiles(project)` считается
  в строке 86, а затем ещё раз внутри `Zip(project)` (`GamePackage.cs:67`). Для проекта
  с сотнями диалогов это двойная сериализация на каждое нажатие «Экспорт ZIP».
  **Сделать:** считать карту один раз и передавать её в упаковщик.
- **P2 · Перезапись без резервных копий и без атомарности.**
  `DialogueGameExport.WriteFiles` (`DialogueGameExport.cs:144-161`) и
  `GamePackage.WriteZip` (`GamePackage.cs:80-89`) пишут через `File.WriteAllBytes`.
  В UI есть подтверждение перезаписи (`ShellViewModel.cs:1107-1110`), но откатить её нечем.
  **Сделать:** `.bak` рядом с перезаписываемым файлом (или один ZIP-бэкап пакета) и запись
  через временный файл.
- **P3 · Имя файла диалога берётся из `sourceFile` без санитизации.**
  `DialogueGameExport.SourceFileName` (`DialogueGameExport.cs:168-180`) вырезает каталог, но не
  запрещённые для Windows символы (`:`, `*`, `?`). **Сделать:** общий санитайзер имени
  (`ProjectFileService.SanitizeName`, `ProjectFileService.cs:15`).

**Добавить**

- Экспорт «только изменённых» файлов (дифф против снапшота gamedata) — основной сценарий
  мододела; сейчас пакет всегда полный (`GamePackage.Zip`, `GamePackage.cs:61-77`).
- Манифест пакета (`export.json`: список файлов, кодировки, версия проекта) для проверки
  установки на чистой gamedata.
- Отчёт экспорта в файл: сейчас результат живёт только в статусной строке
  (`ShellViewModel.cs:1124-1126`).

### 2.4. Quests — анализ и экспорт

Файлы: `Quests/QuestAnalysis.cs`, `Quests/QuestExport.cs`, `ViewModels/QuestsViewModel.cs`.

**Недоработки**

- **P2 · История хранит полный JSON всех квестов на каждый шаг.**
  `QuestsViewModel.cs:28` (`new History<string>(50)`) и `QuestsViewModel.cs:463-464`
  (`JsonSerializer.Serialize(_project.Quests, ...)` → `Push`). Для `task_manager` с сотнями
  квестов это до 50 полных копий списка в памяти, плюс сериализация на каждое действие.
  **Сделать:** снапшот только изменяемого квеста (или патч-дифф), полный список собирать при
  применении истории.
- **P3 · Undo пересоздаёт объекты квестов.** `QuestsViewModel.ApplyHistory`
  (`QuestsViewModel.cs:476-487`) десериализует весь список — ссылки, по которым построены
  элементы списка и выделение, теряются. **Сделать:** обновлять существующие объекты по `id`
  (тот же приём, что кэш VM «по ссылке на модель» из правил проекта).

**Улучшения**

- **P2 · История не помечает проект изменённым при откате.** `AfterHistoryChange`
  (`QuestsViewModel.cs:489+`) обновляет состояние, но признак `Dirty` оболочки выставляется
  только через явные `SetDirty(true)` — проверить, что undo/redo тоже его выставляет
  (иначе правки можно потерять при закрытии, см. §2.2).
- **P3 · Экспорт без выбора формата.** Формат определяется по данным (см. §2.3), а не
  пользователем; для целевой игры с одним форматом это удобно, для смешанного проекта — нет.

**Добавить**

- Экспорт только выбранных квестов / цепочек (в `QuestsViewModel` есть фильтры и «цепочки»,
  но выгрузка всегда общая).

### 2.5. Gamedata — скан и импорт

Файлы: `Gamedata/GamedataScanner.cs`, `Gamedata/GamedataModels.cs`,
